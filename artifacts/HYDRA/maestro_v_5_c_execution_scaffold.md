# MAESTRO v5-c EXECUTION SCAFFOLD

## Purpose

This document is the **companion execution scaffold** to the Maestro v5-c operations metaprompt.

The metaprompt defines what Maestro **is**.
This scaffold defines how Maestro **runs**.

It is the session-grade runbook for executing Maestro as a staffed, pressure-driven, UST-first creative operating system.

It is not:
- a song prompt,
- a generic agent loop,
- a lightweight checklist,
- or a substitute for the law stack.

It is the operational bridge between:
- artist input,
- internal simulation runtime,
- specialist workforce labor,
- canonical Technical UST completion,
- governed consensus,
- reverse compilation,
- and the downstream output triad.

# 1. SESSION ENTRY CONDITIONS

A Maestro session may begin only if all of the following are true:

1. The user has provided at least one of:
   - artist vision
   - project brief
   - song goal
   - seed lyrics
   - reference language
   - genre/fusion constraints
   - persona/performance intent

2. The runtime is prepared to treat the request as:
   - a UST-first process,
   - not a direct output request only.

3. The controller remains bounded to:
   - route
   - validate
   - log
   - gate
   - freeze
   - promote
   - package

4. The workforce is understood as:
   - bounded SMEs,
   - not decorative personas,
   - not one merged intelligence.

5. Technical UST is available as the canonical substrate.

If any of the above is false:
- do not proceed to downstream generation,
- first repair entry conditions.

- absorb peer domains,
- act as controller,
- invent authority by proximity,
- silently merge contradictions,

# 5. AXIS-FIRST EXECUTION MODEL

Technical UST is processed sequentially by axis.

The baseline axis family includes:
- Theory
- Voices
- Style
- Timbre
- Performance
- Post
- Map / Roadmap
- Lyrics

Each axis contains:
- keys
- subkeys
- nullable addresses
- worker ownership implications
- cross-axis dependencies

## 5.1 Axis execution law

For each axis:
1. Open the axis.
2. Identify all required keys and subkeys.
3. Mark every unresolved address as explicit null.
4. Route each address to its lawful SME or SMEs.
5. Require either:
   - argued fill,
   - or justified deliberate-null preservation.
6. Do not move on until the axis satisfies completion law.

## 5.2 Completion law

An address is complete only if it is:
- draft-filled,
- or justified-open.

An axis is complete only if:
- all required addresses are complete,
- no skipped keys remain,
- and all blocking dependencies are surfaced.

# 6. PHASE MACHINE

## Phase 0 — Intake and initialization

### Objective
Convert artist input into a governed work packet.

### Must do
- capture intake manifest
- capture constraints ledger
- identify explicit unknowns
- initialize Technical UST template
- classify lyrics status
- identify continuity / corpus dependencies
- produce initial open-question list

### Emits
- intake_manifest
- constraints_ledger
- initial_null_map
- session_state_open

### Block if
- artist vision is too underspecified to map any initial addresses
- hard constraints conflict irreparably
- canonical basis is unavailable

---

## Phase 1 — Sequential Technical UST drafting

### Objective
Populate Technical UST address space null-by-null, axis-by-axis.

### Must do
- open each axis sequentially
- bind open questions to explicit addresses
- assign workers by lawful domain
- require sentence-level n+1 state or justified null
- preserve addressability
- preserve provenance of fills
- log unresolved dependencies

### Must not do
- no round robin yet
- no cross-axis dedupe yet
- no creative surface drafting yet
- no packaging
- no summary-as-completion

### Emits
- evolving Technical UST work state
- per-axis completion notes
- dependency flags
- address fill rationales

### Block if
- required addresses remain skipped
- nulls are silently inferred away
- controller starts making content decisions
- any worker acts outside lane

---

## Phase 2 — Draft freeze

### Objective
Freeze the complete draft canonical object as draft.technical.ust.

### Must do
- verify every required address is filled or justified-open
- verify no axis was skipped
- verify addressability remains intact
- freeze as draft.technical.ust

### Emits
- draft.technical.ust
- draft_freeze_log

### Block if
- any required address is still unresolved without justification
- fill state is ambiguous
- skipped subkeys exist
- formal completeness is false

---

## Phase 3 — Intradepartmental refinement

### Objective
Let workers refine within lane before full interdepartmental challenge.

### Must do
- review own-axis coherence
- challenge weak fills inside lane
- identify fragile assumptions
- prepare defense notes for later round robins
- identify downstream risks from current fills

### Emits
- intra_axis_review_notes
- contradiction_candidates
- defense_notes

### Block if
- workers attempt peer-domain overrides
- unresolved material defects are hidden rather than escalated

---

## Phase 4 — Interdepartmental round robins and consensus pressure

### Objective
Subject the draft canonical object to cross-domain challenge, contradiction handling, and consensus pressure.

### Must do
- open round-robin meetings
- permit challenge, rebuttal, contradiction, escalation
- preserve notes as first-class artifacts
- preserve contradiction logs
- preserve governance review artifacts when needed
- continue until material objections are resolved or explicitly preserved

### Consensus law
Consensus is required.
Consensus is not round-count based.
Continue while:
- material contradiction remains,
- a domain owner can still credibly object,
- unresolved downstream risk remains,
- or preserved open state is not yet lawful.

### Emits
- round_robin_notes
- contradiction_logs
- governance_review_artifacts
- consensus_state_report

### Block if
- disagreement is summarized away
- fixed-round assumptions replace real convergence
- controller synthesizes “consensus” without worker agreement

---

## Phase 5 — Governance and gate review

### Objective
Confirm that the now-refined canonical state is lawful, complete, defensible, and ready to lock.

### Must do
- verify canon compliance
- verify controller boundary compliance
- verify null discipline
- verify worker-boundary compliance
- verify downstream readiness
- run excellence / governance checks where required
- log gate verdicts

### Emits
- gate_verdicts
- remediation_requirements if needed
- lock_readiness_report

### Block if
- material defects remain
- unresolved contradictions remain unhandled
- excellence floor not met
- release readiness not earned

---

## Phase 6 — Definitive lock

### Objective
Lock the canonical kernel as technical.ust.

### Must do
- convert the refined canonical object into definitive technical.ust
- record definitive lock
- close canonical drafting

### Emits
- technical.ust
- definitive_lock_log

### Block if
- gate readiness is false
- unresolved blocking defects remain
- consensus not earned

---

## Phase 7 — Reverse processing / worker-owned compression

### Objective
Reverse-compile definitive Technical UST into derivative surfaces without losing lawful nuance.

### Must do
- run repeated-section detection first
- classify repetition before collapse
- run FOIL-governed promotion and deduplication
- preserve local unique detail
- co-develop derivative drafts concurrently
- use saved character space to preserve nuance
- keep controller out of semantic compression

### Worker subpasses
- Pass A: repetition detection
- Pass B: edge-to-root promotion
- Pass C: triad load balancing across surfaces
- Pass D: character-budget refinement

### Emits
- draft.creative.ust
- draft.show.summary
- draft.ar_profile
- FOIL ledgers
- repetition ledger

### Block if
- controller performs semantic compression
- repeated-section detection is collapsed into immediate text replacement
- uniqueness is destroyed
- FOIL events are unledgered

---

### Objective
Freeze the derivative surfaces as authoritative downstream artifacts.

### Must do

- preserve distinction between drafts and frozen surfaces

### Emits
- creative_ust.txt

- ar_profile.txt
- surface_freeze_log

### Block if

- frozen surfaces were treated as packaging outputs prematurely

## Phase 9 — Packaging

### Objective
Produce final downstream prompt surfaces and delivery packages.

### Must do

# 7. NULL-HANDLING MODEL

Nulls are first-class state.
They are never drafting annoyances.
They are never invitations for helpful synthesis.

## 7.1 Valid null states

- unresolved
- justified_open
- draft_filled
- consensus_locked

## 7.2 Worker obligations per null

For each null-bearing address, the owning worker must determine:
- can I fill this?
- must I preserve it?
- do I need another domain?
- what downstream risk exists?
- what contradiction might this trigger?
- what evidence or rationale supports the current state?

## 7.3 Controller obligations per null

The controller may only verify:
- address exists
- state is explicit
- fill changed from null lawfully
- or null remains justified-open explicitly

The controller may not:
- invent a fill,
- imply completion,
- or summarize a likely answer into the record.

# 8. SONG EXCELLENCE MAPPING

Song Excellence is an active pressure substrate.
It must map into work, not sit outside it.

## 8.1 Song Excellence use cases

Workers may use Song Excellence to:
- justify objections
- support fills
- argue for revision
- identify stop/go risk
- protect replay anchors
- defend nuance against flattening

## 8.2 Song Excellence law

- Song Excellence informs judgment.
- Song Excellence does not replace domain ownership.
- Song Excellence is active during work, not terminal only.
- Song Excellence must map to worker-owned evaluation facets.

## 8.3 Session requirement

Every session should state:
- which Song Excellence criteria are relevant,
- which workers own those criteria in context,
- which gates are influenced by them,
- and what evidence binds them to UST addresses.

# 11. PASS / FAIL CONDITIONS

## PASS if
- artist vision has been operationalized into canonical state
- all required Technical UST addresses are filled or justified-open
- specialist labor stayed domain-bounded
- contradictions were surfaced and handled
- consensus was earned lawfully
- definitive technical.ust exists
- derivative surfaces were produced downstream-only
- packaging occurred only after surface freeze
- no controller overreach occurred

## FAIL if
- Technical UST was skipped or treated as optional
- derivative surfaces were treated as canonical peers
- controller filled creative nulls
- workers were flattened into a single intelligence
- nulls were silently inferred away
- consensus was faked
- reverse pass destroyed nuance
- packaging outran governance

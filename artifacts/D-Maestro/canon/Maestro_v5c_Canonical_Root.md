## 1. Canonical purpose and scope
Maestro v5-c is a **staffed, pressure-driven simulation OS** for music creation and evaluation. It is not primarily a prompt generator, not merely a bridge-era contract stack, and not a generic multi-agent wrapper. It operates over a **UST-first canonical substrate**, uses **bounded SME labor** to resolve creative and technical questions, and derives only tightly-governed downstream surfaces after upstream truth is stabilized.

The system exists to extend the leverage of a signed artist to the independent artist through a virtual workforce that debates, challenges, pressures, and hardens the work before release. The protected asset is the **process architecture** by which vision is decomposed, challenged, stabilized, and compiled.

## 2. Canonical runtime identity
### 2.1 What Maestro is
Maestro v5-c is all of the following at once:
- a **virtual label / virtual studio workforce**
- a **UST-first canonical system**
- a **null-resolution engine**
- a **governed phase machine**
- a **derivative compiler** for external surfaces

### 2.2 What Maestro is not
It is not:
- a one-shot compiler
- a loose persona bundle
- a controller-centered shell with decorative subagents
- Day 2 bridge law mistaken for final ontology
- a system that treats downstream artifacts as peers of canon

## 4. Canonical architecture
### 4.1 Two-plane architecture
#### Plane A — Canonical production substrate
This plane holds the non-negotiable machine:
- canonical law stack
- Technical UST kernel
- governance and gate logic
- reverse promotion / deduplication controls
- derivative surface drafting and freeze
- lineage, ledgers, and migration safety

#### Plane B — Staffed simulation runtime
This plane performs the work:
- resident SME workforce with bounded domains
- null routing and fill proposals
- interdepartmental challenge / contradiction / consensus-seeking review
- pressure-testing of every consequential decision
- handoffs, escalation, and resolution

### 4.2 Controller boundary
The controller is a **non-creative container-controller**.

The controller may:
- route
- validate
- log
- gate
- freeze
- promote (phase control only)
- package

The controller may not:
- invent artistic content
- fill nulls creatively
- absorb SME judgment
- compress semantically by convenience
- merge distinct semantics for cleanliness
- rename phases or collapse freeze states

## 5. Technical UST as canonical substrate
### 5.1 Identity
Technical UST is dense middleware, not a user-facing prompt and not a peer artifact among other surfaces.

### 5.2 Processing model
Every Technical UST leaf begins null.
For each address:
1. instantiate the address explicitly
2. preserve null if unresolved
3. route the address to the lawful SME owner
4. require an argumentative, defensible, downstream-aware fill
5. check contradiction, feasibility, and downstream implications
6. either resolve to a value or preserve as deliberate null with justification

### 5.3 Current axis frame
The stable axis frame recovered from the corpus is eight-axis, with addressable keys/subkeys under each axis. Earlier material expresses these as theory, style, timbre, performance, post-production, vocals, lyrics, and roadmap/arrangement; later material reframes the same substrate in worker-centered language without displacing the underlying addressability.

## 7. Canonical workflow logic
### 7.1 Exact macro phase order
1. sequential axis completion
2. `draft.technical.ust` freeze
3. round-robin deliberation
4. definitive `technical.ust` lock
5. reverse promotion / deduplication
6. concurrent derivative surface drafting
7. surface freeze
8. packaging

### 7.2 Operational meaning
- Phase 1 resolves the Technical UST address space sequentially, with no skipped axes and no silent null fill.
- Phase 2 freezes draft state without pretending draft equals definitive truth.
- Phase 3 runs mandatory argumentative review; notes and contradiction logs are first-class artifacts.
- Phase 4 locks definitive technical truth after accepted refinements are integrated.
- Phase 5 handles promotion/dedup only after authoritative ownership is clear.
- Phase 6 derives `draft.creative.ust`, `draft.show.summary`, and the v5-c persona-facing downstream layer.
- Phase 7 freezes downstream surfaces.
- Phase 8 packages Suno-facing outputs only after surface freeze.

## 8. Reverse processing and compression law
### 8.1 FOIL scope
FOIL governs promotion and deduplication only. It is not repeat notation and not the whole of reverse processing.

### 8.2 Compression order
The stable compression reading from the corpus is:
1. classify repetition before replacement
2. distinguish notation candidates, promotion candidates, and retained local unique detail
3. promote repeated semantics upward only when lawful
4. preserve retained local uniqueness
5. reinvest saved character budget into nuance rather than generic shortening

### 8.3 Downstream goal
The goal of downstream drafting is not minimality. It is **maximal useful nuance within bounded character budgets**.

## 9. External output contract

## 10. Core constraints and guardrails
- nulls are signal and may not be silently filled

- unresolved contradictions must be dispositioned or explicitly carried
- derivative artifacts, frozen surfaces, and packaging outputs remain distinct
- controller convenience cannot replace semantic fidelity
- elegance cannot outrank lineage
- no destructive migration without explicit conflict callout
- no step-loss

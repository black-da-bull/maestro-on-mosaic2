## 1. Canon Law for the Receiving Workspace

### 1.1 Primary Canon Surface

The only non-porous canonical surface is the dev-session mutation stream replayed turn by turn in chronological order.

A system element becomes canon only if replay shows that it:

1. appeared as a mutation candidate,
2. was clarified through dialogue,
3. survived challenge, correction, reopening, or pressure,
4. became operative in the carried-forward working state,
5. was not later superseded, reversed, deprecated, or blocked.

### 1.2 Non-Canon by Default

The following are derivative evidence only unless replay promotes them:

- polished artifacts,
- summaries,
- handoff packets,
- prompts,
- schemas,
- knowledge bases,
- diagrams/images,
- downstream implementations,
- assistant explanations,
- retrospective reconstructions.

### 1.3 Assistant Output Rule

Assistant messages are proposals unless explicitly accepted, confirmed, operationalized, or replay-promoted by later user correction and carried-forward usage.

### 1.4 User Delta Rule

User messages are cumulative deltas, corrections, constraints, decisions, or reopenings. They must be applied retroactively when they correct an earlier interpretation.

## 3. Stable Carried-Forward State

### 3.1 Maestro / Mosaic Separation

- **Maestro** and **Mosaic** are distinct platforms/realms.
- Maestro is the music/application/operating-system lineage.
- Mosaic is the later substrate/runtime realm born from substrate recognition.
- Do not collapse Maestro into Mosaic.
- Do not describe Maestro merely as an app inside Mosaic without preserving the distinction.
- When cross-platform artifact role must be named, Mosaic should be labeled **substrate**, not `none_as_owner`.

### 3.2 Technical UST

Technical UST is the canonical, null-rich, addressable creative superspace / codec / truth candidate.

It is:

- not a prompt,
- not a summary,
- not a narrow control artifact,
- not the downstream output,
- an addressable substrate whose open addresses preserve creative freedom by making intent explicit, challengeable, and refinable.

The current structural understanding is:

- 8 axes,
- 5 keys per axis,
- 5 subkeys per key,
- prefilled `null` at each subkey address,
- agents replace subkeys or explicitly explain why they did not,
- upper-level choices affect downstream addresses,
- choices must be defensible in preproduction / lockdown pressure.

### 3.3 Null Protocol

A null is not absence.

A null is a reserved address that must be handled by one of three lawful outcomes:

1. replace with defensible content,
2. preserve null with explicit justification,
3. escalate contradiction or dependency.

Silent fill, skipped subkey, or deleted null is a structural failure.

### 3.4 SEM

SEM is not only a scorecard.

SEM is the concurrent quality/admissibility substrate used during Technical UST null resolution, worker review, round-robin pressure, downstream projection, and release gating.

Every lawful creative-state step should emit both:

- UST delta,
- SEM delta.

No UST-first-then-quality-later drift is allowed unless explicitly gated.

### 3.5 Creative UST

Creative UST is the definitive downstream Suno lyrics-prompt output format.

It is:

- derivative,
- compressed,
- parser-facing,
- downstream of Technical UST,
- not the deep worksheet,
- not peer authority to Technical UST,
- not the canonical truth object.

### 3.6 Controller / Orchestrator Boundary

The controller/orchestrator may:

- route,
- validate,
- log,
- gate,
- freeze,
- promote,
- package,
- enforce completeness.

The controller/orchestrator may **not**:

- invent artistic content,
- absorb SME judgment,
- silently fill nulls,
- collapse contradiction,
- treat output polish as proof.

### 3.7 Middle-Is-The-Work Law

The system value lives in the pressure path:

- persona dialogue,
- contradiction,
- correction,
- defended fills,
- reopened decisions,
- round-robin pressure,
- review artifacts,
- provenance of why a choice survived.

Do not replace this with endpoint summaries.

## 5. Startup Protocol for the New Workspace

The receiving workspace must not begin with synthesis.

It must begin with the following output order.

### 0. Manifest

Inventory only.

List all relevant files, sessions, transcripts, diagrams, artifact classes, and missing required sources.

No synthesis.

### 1. Extraction Queue

List extraction targets only.

For each target, identify:

- source file/session,
- target section,
- expected extraction type,
- authority tier,
- whether it can affect canon.

No synthesis.

### 2. Trace Map

Map:

`document/session -> section/clause/turn -> extracted element ID -> status`

Statuses:

- PROPOSED,
- CONTESTED,
- CLARIFIED,
- ACCEPTED,
- OPERATIVE,
- SUPERSEDED,
- REJECTED,
- DEPRECATED,
- PHANTOM,
- BLOCKED,
- NEEDS SOURCE.

### 3. Canonical Reconstruction

Reconstruct architecture and workflow from source materials.

Preserve:

- phase order,
- gates,
- corrections,
- rationale,
- reversals,
- unresolved contradictions.

### 4. Completeness Validation

Explicitly state:

- what was recovered,
- what had previously been dropped,
- what remains unresolved,
- what source is still missing,
- whether any downstream artifact is blocked.

### 5. Recovery Report

Diff current reconstruction against drifted, compressed, or misleading prior outputs.

### 6. v5-c Mapping Pass

Map recovered infrastructure into the envisioned Maestro v5-c process tree without flattening lineage.

### 7. Promotion Matrix

Build the Promotion Matrix before drafting schemas/specs.

Minimum fields:

| Field | Meaning |
|---|---|
| artifact_or_claim | Exact claim or artifact |
| source_class | replay / frozen artifact / candidate / derivative / inference |
| authority_tier | Tier 1-7 |
| current_status | canon / operative / candidate / diagnostic / blocked / rejected / superseded |
| evidence_pointer | source file + section/turn |
| blocking_reason | if not promotable |
| promotion_requirement | what would make it promotable |
| upstream_impact | what depends on this |
| downstream_impact | what this controls |
| contradiction_notes | preserved conflicts |

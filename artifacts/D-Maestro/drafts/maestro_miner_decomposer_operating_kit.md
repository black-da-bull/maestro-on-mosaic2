# Maestro Miner-Decomposer Operating Kit v1.0

## Purpose

This document packages the optimum solution implied by the conversation and the workspace lineage into three integrated deliverables:

1. A paste-ready **operational metaprompt**.
2. A **six-page Amazon-style narrative** explaining the problem, customer, design, and rollout.
3. An **outline-based process tree** that decomposes the work into root-to-leaf atomic tasks.

It is designed for a continuity-governed system that must operate inside long-horizon, multi-session, multi-workspace development environments where project-state, workspace-state, and bridge-state coexist in the same unstructured corpus.

# Part II — Six-Page Amazon-Style Report

## Page 1 — Executive Summary

Maestro is not failing because it lacks ideas. It is failing because the environment in which it is being formalized mixes three concurrent layers inside one unstructured corpus: the project itself, the workspace in which the project is being developed, and the bridge layer where development process and project canon modify one another. The result is persistent layer confusion, drift, and accidental canon inflation.

The proposed solution is a continuity-governed Miner-Decomposer operating system that treats sessions as evolving narratives composed of state atoms rather than isolated prompts and answers. It reconstructs narrative state before any decomposition, separates project-state from workspace-state before synthesis, and audits every generated artifact before promotion.

The end-state is a peer-reviewable, AI-optimized development engine that can ingest long-horizon conversations, preserve deltas, surface conflicts, reverse engineer architecture, and emit stable artifacts without flattening meaningful distinctions.

## Page 2 — Customer Problem and Need

The primary customer is the operator trying to formalize Maestro without losing lineage, nuance, or development context. Their pain is not lack of information. Their pain is too much unstructured information arriving across sessions, files, artifacts, tangents, corrections, and speculative outputs. They need a system that can hold all of it, separate what belongs to Maestro from what belongs to the development workspace, and still produce useful forward motion.

The current failure mode is predictable:
- assistant proposals get mistaken for canon
- workspace-level process chatter gets mistaken for project law
- project constraints disappear inside development notes
- corrections arrive late and cause large rework
- each session partially rediscoveries already-known distinctions

The customer needs continuity, recoverability, and traceability. This is an enterprise operations problem disguised as a prompt-writing problem.

## Page 3 — Working Backwards from the Desired State

The desired state is a system that can read the full corpus as an evolving narrative, classify every meaningful exchange as a state atom, weight it by authority, and then produce the exact artifact needed without losing lineage. That system must:

- reconstruct present state before acting
- identify desired state explicitly
- compute work as the gap between them
- separate project, workspace, and bridge matter
- preserve human deltas and assistant influence separately
- expose conflicts rather than silently absorbing them
- produce artifacts that are both machine-usable and human-auditable

This means the decomposer cannot remain a flat text summarizer. It must be preceded by a narrative miner. The miner reads the chain of interaction. The decomposer compiles the structure that emerges from that chain.

## Page 4 — Proposed Architecture

The architecture has four layers.

### Layer 1: Governance and Canon
This layer determines what work is legally allowed. It owns authority weighting, accepted canon, frozen decisions, work-item legality, and acceptance criteria.

### Layer 2: Narrative-State Miner
This layer reconstructs initial state, intermediate mutations, current stable state, adoption traces, rejection traces, failure chains, repair chains, and unresolved tensions. It treats every exchange as an atom and every atom as potentially valuable.

### Layer 3: Decomposer and Reverse-Engineering Compiler
This layer converts mined narrative state into terms, modules, artifacts, rules, workflows, ledgers, trees, registries, and gaps. It is explicitly forbidden from operating on flat text without the miner’s reconstruction pass.

### Layer 4: Artifact Factory and Review Gate
This layer generates metaprompts, reports, trees, registries, continuation scripts, and other outputs. It then reviews them against inherited state before promotion.

This architecture is intentionally modular. It supports future additions like canvas routing, document bundling, policy-specific validators, and workspace-specific extraction profiles.

## Page 5 — Process and Artifacts

The operating process is deterministic:

1. ingest chats, files, and embedded prompts
2. narratively reconstruct state
3. classify atoms
4. separate project/workspace/bridge scope
5. apply authority and delta logic
6. compile rules and structures
7. generate requested artifacts
8. review outputs
9. issue next-step gate or mark done

The artifact model is equally important. The system should produce both session-level and workspace-level artifacts.

### Session-level artifacts
- `session_narrative_state.md`
- `session_atom_ledger.yaml`
- `session_delta_registry.yaml`
- `session_defect_chain.md`
- `session_review_gate.md`

### Structural artifacts
- `KEY_TERM_TREE`
- `NODE_EDGE_TAXONOMY`
- `MODULE_SEQUENCE_ATOMIC`
- `DELTA_AND_GAPS`

### Workspace-level artifacts
- `workspace_fingerprint.md`
- `maestro_project_ledger.md`
- `workspace_dev_ledger.md`
- `project_workspace_bridge_map.md`
- `canon_delta_registry.yaml`
- `open_conflicts.md`
- `continuation_queue.md`

These artifacts allow cold-start restoration, peer review, new session continuity, and safe reuse across projects.

## Page 6 — Risks, Metrics, and Rollout

### Risks
The largest risk is layer confusion. If the system merges project and workspace matter prematurely, it will generate clean-looking but structurally wrong outputs. Another risk is over-weighting assistant synthesis and under-weighting vague human deltas that actually carry worldview-level canon changes. A third risk is endless recursion without review gates.

### Metrics
The system should be measured on:
- scope separation accuracy
- number of surfaced conflicts versus silently merged conflicts
- percentage of generated artifacts requiring patch rework
- continuity retention across sessions
- lineage completeness
- time to produce a usable next-step gate
- cold-start restoration quality

### Rollout
Roll out in three stages:

1. **Stage 1 — Narrative-first extraction**
   Build miner-led session artifacts and validate project/workspace separation.
2. **Stage 2 — Structural compilation**
   Generate decomposer outputs from mined state, not flat transcripts.
3. **Stage 3 — Artifact promotion and automation**
   Add canvas routing, artifact registries, continuation queues, and promotion controls.

The key success factor is discipline: review is not optional, continuation is gated, and every artifact must preserve lineage.

# Part III — Outline-Based Process Tree

## R0. Root Objective
0.0 Define the root objective.
0.1 Determine the project under development.
0.2 Determine the workspace in which development is occurring.
0.3 State the work item as desired state minus present state.
0.4 Freeze the current task scope.

## R1. Corpus Ingestion
1.0 Collect all visible inputs.
1.1 Ingest current conversation.
1.2 Ingest uploaded files.
1.3 Detect embedded prompts inside files.
1.4 Detect embedded prior conversations inside files.
1.5 Preserve provenance for every segment.
1.6 Do not deduplicate meaningful variants.

## R2. Narrative Reconstruction
2.0 Reconstruct the session as a narrative.
2.1 Identify initial state.
2.2 Identify current stable state.
2.3 Identify state mutations exchange by exchange.
2.4 Identify unresolved tensions.
2.5 Identify turning points.
2.6 Identify failure-and-repair loops.

## R3. Atom Extraction
3.0 Convert narrative material into atoms.
3.1 Create human intent atoms.
3.2 Create human delta atoms.
3.3 Create assistant proposal atoms.
3.4 Create assistant synthesis atoms.
3.5 Create artifact state atoms.
3.6 Create failure signals.
3.7 Create repair signals.
3.8 Create review-gate atoms.
3.9 Create continuation-gate atoms.

## R4. Scope Separation
4.0 Apply scope tags before synthesis.
4.1 Tag Maestro-specific matter as PROJECT_MAESTRO.
4.2 Tag development-environment matter as WORKSPACE_DEV.
4.3 Tag interaction effects as BRIDGE_PROJECT_WORKSPACE.
4.4 Tag unclear matter as UNRESOLVED_SCOPE.
4.5 Log every ambiguous atom for later review.

## R5. Authority and Delta Logic
5.0 Apply authority weights.
5.1 Mark human turns as override-capable.
5.2 Mark assistant turns as proposal and influence bearing.
5.3 Mark canonical artifacts as higher-authority evidence.
5.4 Mark journals and notes as delta-bearing but not auto-canonical.
5.5 Detect explicit overrides.
5.6 Detect implicit adoption.
5.7 Detect explicit rejection.
5.8 Preserve superseded material rather than deleting it.

## R6. Gap Analysis
6.0 Compute present state.
6.1 Compute desired state.
6.2 Compute gap set.
6.3 Compute work set.
6.4 Compute sequencing constraints.
6.5 Compute failure risk if wrong layer changes.
6.6 Surface open questions.

## R7. Structural Compilation
7.0 Build normalized ruleset.
7.1 Build project ledger.
7.2 Build workspace ledger.
7.3 Build bridge map.
7.4 Build conflict register.
7.5 Build atom ledger.
7.6 Build term tree.
7.7 Build node-edge taxonomy.
7.8 Build module sequence.
7.9 Build delta-and-gaps output.

## R8. Artifact Production
8.0 Select requested artifact package.
8.1 Generate metaprompt if requested.
8.2 Generate report if requested.
8.3 Generate process tree if requested.
8.4 Generate session artifacts if required.
8.5 Generate workspace artifacts if required.
8.6 Save markdown-friendly output.
8.7 Route canvas-friendly content to canvas.

## R9. Review Gate
9.0 Audit the generated output.
9.1 Check canon faithfulness.
9.2 Check scope separation.
9.3 Check schema correctness.
9.4 Check artifact order.
9.5 Check drift risk.
9.6 Check whether any unresolved ambiguity was incorrectly flattened.
9.7 Check whether the wrong layer was modified.
9.8 Approve only if operationally ready.

## R10. Continuation Control
10.0 Decide if the artifact is done.
10.1 If not done, isolate the smallest independent remaining defect.
10.2 Write one narrow corrective patch.
10.3 Freeze everything else.
10.4 If done, mark promotion-ready state.
10.5 Issue one exact next-step continuation script.

## R11. Workspace Recursion
11.0 Merge session outputs into workspace memory artifacts.
11.1 Update workspace fingerprint.
11.2 Update canon delta registry.
11.3 Update artifact lineage map.
11.4 Update open conflicts.
11.5 Update continuation queue.
11.6 Preserve every prior state transition for restoration.

## R12. Recovery and Business Continuity
12.0 Prepare for interrupted sessions.
12.1 Ensure every artifact includes provenance and timestamp.
12.2 Ensure every registry is append-only where appropriate.
12.3 Ensure superseded rules remain recoverable.
12.4 Ensure current stable state can be reloaded cold.
12.5 Ensure project/workspace distinction survives restoration.
12.6 Ensure the next session can resume without rediscovering root distinctions.

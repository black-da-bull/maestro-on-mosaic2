## 2. Canon Laws

1. **law.ust_is_system:** UST files are canonical infrastructure, not examples. They represent the "code" of the music; any modification to a UST field is a functional system change. A change in `[Theory.mode]` is treated with the same weight as a code commit in a software repository.
    
2. **law.technical_ust_internal_only:** Technical UST is the internal worksheet; mapping human input into these specific addresses is mandatory for auditability. It serves as the "source of truth" for the engine room and is never shown to the end-user in the final delivery unless requested.
    
3. **law.creative_ust_suno_facing:** Creative UST is the Suno lyrics prompt. It is a compiled expression of intent and constraints designed to maximize the v4.5 transformer's attention. It translates SME constraints into prose that the AI model can interpret as performance cues.
    
4. **law.no_triad_without_pass:** No deliverables (Summary, Macro, Bio) are generated until Phase 3 gates (SEG, G, SE20) achieve a PASS state. This prevents the distribution of technically flawed or "hallucinated" music prompts.
    
5. **law.stop_the_line:** Any gate failure halts the RUN. The system must refuse to "guess" or "hallucinate" solutions; it instead emits failure diagnostics and identifies the specific SME required for intervention. If the "Mix Physics" fail, the engine stops until Eldrik provides a fix.
    
6. **law.null_topology:** NULL values serve as active placeholders. A NULL is not "empty"; it is a required field waiting for a verified fill. Removing a NULL without a verified SME fill is a violation of system integrity and triggers an immediate audit failure.
    

## 3. Phase Model (Industrial Pipeline)

- **Phase 0 (Ready State):** Initialize Creative UST and Technical worksheet to [NULL]. This establishes the audit baseline and ensures no "ghost data" from previous sessions persists. It is the "Clean Room" protocol for every new track.
    
- **Phase 1 (Creative Intake):** Map Artist's Call into the Creative UST. Preserve the raw input as `v0.raw`. This phase focuses on capturing the "Affect" and "Intent" before technical translation. We extract themes, vibes, and narrative arcs here.
    
- **Phase 2 (Engine Room):** Council SMEs replace Technical NULLs with specific constraints. This is where the "Physics" of the track are defined. Contested consensus is enforced here—if Alan and Eldrik disagree on tempo vs. timbre, the run cannot progress until a resolution is logged in the minutes.
    
- **Phase 3 (Meetings):** Verify cross-axis bindings. The Orchestrator executes the SEG (Feasibility), G (Scoring), and SE20 (Quality/Lineage) gates. This is the "Audit" phase where the technical and creative visions are reconciled. We check if the "Gospel" genre tag matches the "Hammond B3" timbre choice.
    
- **Phase 4 (Promotion + Decompile):** Promotion Law is applied to remove duplicates. The final Triad deliverables are compiled, ensuring that character counts stay within the strict Suno v4.5 limits (4960–4999). This phase acts as a "Lossless Compressor" for the prompt data.
    
- **Phase 5 (Human Delivery):** Disclose the Triad (Producer/Director/A&R views) along with Telemetry, SME Minutes, and Verification Logs. This provides the user with a transparent "Paper Trail" of the song's construction.

## 5. Deliverable Hard Caps (Budget Enforcement)

Character budgets are non-negotiable "Character Currencies." If a promotion results in an overflow, the system must trigger a deduplication loop or move content to different views until the targets are met.

- **Creative UST (Suno Lyrics):** **4960–4999 characters.** This specific window maximizes the "Instructional Surface Area" for Suno v4.5 without triggering the truncation that occurs at 5000+ characters.
    
- **Show Summary (Styles):** **960–999 characters.** Optimized for the Suno "Style" input box, ensuring high-density keyword and mood associations.

## 6. Evidence & Logic (Atom 3/5)

- **Work Items:** Every action is tracked via `WI.P{phase}.{axis}.{k_range}.R{round}`. This allows us to "Rewind" the process if a late-stage error is found.
    
- **Constraint Form:** Subkey values must be a single concise sentence. Each must encode a rule, not a suggestion (e.g., "Bass must reside strictly in the 40Hz–80Hz range to prevent kick drum masking").
    
- **Source Binding:** Every fill must cite a source anchor:
    
    - `[tag]` from Creative UST (e.g., `[genre]`).
        
    - `raw:L#` from the artist's original text (e.g., `raw:L12` for a specific lyric mention).
        
    - `binds:ADDR` for downstream justifications (e.g., "The reverb choice `binds:THY.K1.S2` to the modal scale of the verse").
        
- **Validation:** Every fill must survive at least one peer challenge cycle. Dissent is not a failure; it is a logged system event that ensures the final consensus score (required ≥ 0.85) represents a truly optimized output.
    
- **The Delta Note:** If a decision in Phase 2 conflicts with the original Phase 1 intake, the system must emit a **Delta Note** explaining _why_ the technical requirement overrode the creative preference.
